# 查询性能与界面修复记录

## 已定位并修复的问题

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| 先扫描、复制全部前缀匹配，再做分页 | 常见前缀匹配越多，联想越慢且内存分配越大 | 对预归一化索引做两次二分查找，仅复制当前页 |
| 原词排序，却用小写词做二分比较 | 大小写混合时二分条件不单调，可能漏词 | 按小写键排序，同键用原词排序，保留原始拼写 |
| API 丢弃 `dict_id`，引擎也未处理 | 选定词典后联想仍混入其他词典 | 使用每本词典的独立索引 |
| 停用通过卸载实现，但不更新全局索引；重载又要求已加载 | 停用后仍出现旧联想，重新启用失败 | 统一持久化与内存启停状态，卸载同步更新索引 |
| 每次重建重新导出词条，还建立未使用的模糊索引 | 重复计算、额外启动成本与内存占用 | 每本词典只导出一次并缓存前缀索引 |
| 中文长度按字节计算，分页未防溢出 | 单个中文字符通过校验，极端页码可能导致异常 | Unicode 字符计数、空白清理、分页边界验证 |
| 重载覆盖标题，标题更新没有引擎锁 | 自定义标题丢失，查询期间存在竞争 | 保留标题，通过引擎锁更新；失败重载保留旧词典 |
| 前端旧请求不取消、不校验请求顺序 | 旧联想/结果覆盖新输入或新词典 | 150 ms 防抖、AbortController 和请求序号保护 |
| Alpine 的 `init()` 同时由框架和 `x-init` 调用 | 页面初始化重复请求 | 保留自动初始化入口 |
| 外部运行时 Tailwind/CDN 依赖 | 网络波动时样式或操作不可用 | 预生成 CSS，固定版本并本地提供脚本 |
| 词典 CSS 直接插入主页面 | 释义样式可能破坏应用或其他释义 | 清理 HTML 后放入独立 Shadow DOM |
| 后台 `uploadStatusText` 未初始化 | 页面加载时出现 Alpine 表达式错误 | 初始化上传状态字段 |

## 界面调整

查询页采用浅色书架布局、深青色主色、独立释义卡片、词典范围选择、查询历史和明确的加载/空结果/错误状态。
手机端保留查询、词典筛选、历史和管理入口；支持方向键选择联想、Enter 查询、Esc 关闭、`/` 聚焦搜索，以及中文输入法组合输入。
后台统一了颜色、表格、上传区域和间距。登录框增加标签关联、焦点管理和键盘关闭。

## 基准测试

执行环境：Linux amd64，AMD EPYC 9V74；Go 1.25.0，`-benchtime=200ms`。
测试数据为合成的 `prefix0000000` 等全小写词条，查询 `pre`，每页 10 条。
所有词条都匹配，用于复现高频前缀的最坏情况。基线复现修改前的收集算法，避开其大小写排序错误。

| 词条数 | 原匹配收集算法 | 新分页查询 | 原查询分配 | 新查询分配 |
| --- | ---: | ---: | ---: | ---: |
| 100,000 | 12.97 ms/op | 0.402 μs/op | 8.92 MB/op | 224 B/op |
| 1,000,000 | 111.24 ms/op | 0.447 μs/op | 88.02 MB/op | 224 B/op |

这些数字仅衡量已加载的内存索引，不代表生产环境 HTTP 延迟，不包含启动索引构建、网络、MDX 释义读取或页面渲染。
查询复杂度从 `O(log N + 匹配数)` 变为 `O(log N + 每页条数)`。启停/加载仍会重建全局索引；大量词典频繁管理时，重建期间仍可能等待引擎锁。

## 验证范围

- Go 全量测试、race detector、`go vet` 和服务构建。
- 前端状态回归测试：请求乱序、清空、词典切换、退出登录、输入法、键盘选择。
- Chromium：本地静态资源、真实登录、MDX 联想与释义查询、桌面与手机页面、后台加载。
- 使用自编微型 MDX 词典及百万词条合成索引；未使用用户实际的大型 MDX/MDD 词库，真实词库的启动耗时、媒体资源和浏览器端总耗时仍需实测。
